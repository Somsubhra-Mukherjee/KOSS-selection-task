What is WebAssembly?

👉 A low-level binary format for the web

👉 Runs at near-native speed

👉 Compile C / C++ / Rust → WASM

💡 Not meant to be written by hand

The motivation behind Web assembly

👉 Near-Native Performance:- WebAssembly enables high-performance execution in the browser, making compute-heavy applications like games, CAD tools, and video editors feasible on the web.

👉 Multi-Language Support:- It allows code written in languages like C, C++, and Rust to run directly in the browser, avoiding the need to rewrite everything in JavaScript.

👉 Secure & Portable Execution:- WASM runs in a sandboxed environment with a compact binary format, ensuring fast, secure, and cross-browser compatibility.

👉 Complementary to JavaScript:- It complements JavaScript by handling performance-critical tasks, while JavaScript manages UI and application logic.

Best Solution: WebAssembly + JavaScript

How WebAssembly Fits into the Web

🔒 WASM Virtual Machine

👉 Runs inside a sandboxed VM

👉 No access to OS / File System / Network

👉 Uses only its own memory

🔗 Interaction Layer

👉 Talks via JavaScript

👉 Uses Web APIs (DOM, WebGL, Fetch)

👉 Access is controlled

WASM Module ➝ WASM VM ➝ Browser ➝ Your System

Key Concepts

Module

Web Assembly binary that has been compiled by the browser into executable machine code. A method is stateless and can be explicitly shared between windows, and workers. A module declares imports and exports just like an ES module.

Memory

A resizable Array Buffer that contains the linear array of bytes read and written by WebAssembly’s low-level memory access instructions.

Table

A resizable typed array of references (e.g. to functions) that could not otherwise be stored as raw bytes in memory.

Instance

A module paired with all the state it uses at runtime including a Memory, Table and set of imported tables.

Using the WebAssembly JS API

JS controls, WASM provides high performance.

They work together via the WASM JS API.

Loading a WASM module:

Old way: Fetch → Convert → Compile → Instantiate

New way (faster):

WebAssembly.instantiateStreaming(
  fetch("file.wasm"), importObject
)

Import Object

WASM cannot access JS directly → must pass functions manually.


const importObject = {
  my_namespace: {
    imported_func: (arg) => console.log(arg)
  }
};

JS provides external functionality called by WASM.

Memory (Linear Memory)

Continuous block of bytes, like raw RAM.


const memory = new WebAssembly.Memory({initial: 10, 
maximum: 100});

Accessing memory:


const data = new DataView(memory.buffer);
data.setUint32(0, 42, true);

Memory is mutable, growing memory invalidates old buffer:

memory.grow(1);

Tables (Function Pointers)

C/C++ uses function pointers → unsafe in raw memory.

Solution: Tables → safe array of function references.

Functions stored in table and passed around by index instead of pointer.

Globals & Multiplicity

Globals: Shared variables between JS and WASM modules.


const global = new WebAssembly.Global({value: "i32", 
mutable: true}, 0);

Multiplicity: One module → many instances, one memory → multiple modules for dynamic linking.

WebAssembly Object & Workflow

JS API:

  1. instantiate() → runs WASM
  2. Memory → manage memory
  3. Table → function storage
  4. Global → shared variables

Workflow:

  1. Load .wasm via instantiateStreaming
  2. Provide imports from JS
  3. Execute exported WASM functions
  4. Share memory, functions & variables

Compiling C/C++ to WASM

Step 1: Setup Emscripten

Install the compiler toolchain to generate WebAssembly from C/C++. 

pip install emscripten
emsdk install latest

The Emscripten toolchain is essential for converting C/C++ code to WASM.

Step 2: Prepare C/C++ Code

Example C program:

#include <stdio.h>
int main() {
  printf("Hello from WASM!\n");
  return 0;
}

Save this as hello.c

Step 3: Compile with Emscripten

emcc hello.c -o hello.html

Output files:

  • ✓ hello.wasm – WebAssembly binary
  • ✓ hello.js – JavaScript glue code
  • ✓ hello.html – Loader page

Step 4: Run in Browser

Important: Use HTTP server, not file:// protocol! 

python -m http.server 8000

Then open http://localhost:8000/hello.html in your browser.

WASM modules require HTTP for security reasons.

Step 5: Call C from JS

// Exported C function
int add(int a, int b) { return a + b; }

// Call from JavaScript
Module.ccall('add', 'number', 
  ['number', 'number'], 
  [5, 3]
);

Use ccall() to invoke C functions from JS.

WebAssembly Text Format

Modules & S-expressions

Everything is a tree in parentheses. The first label identifies the node type. 

(module (memory 1) (func))

Structure: Root is "module", children are "memory" and "func".

WAT is the human-readable representation of WASM binary modules.

Functions

Core executable units with parameters and return types:

(func (param i32) (param i32) (result f64)
  (local i32)
  ;; function body instructions
)
  • ✓ Signature declares parameters & return
  • ✓ Locals are typed variables
  • ✓ Body contains linear instructions

Types & Stack Machine

Numeric Types:

  • i32 – 32-bit integer
  • i64 – 64-bit integer
  • f32 – 32-bit float
  • f64 – 64-bit float

Stack Model: Instructions push and pop values. No direct variable manipulation outside locals.

Memory & Locals

Locals & Parameters:

(local.get $var)
(local.set $var)

Parameters are treated as initialized locals.

Linear Memory:

(memory 1)
(import "js" "mem" (memory 1))

Imports & Exports

Call JS functions or expose WASM functions:

(import "console" "log" (func $log (param i32)))
(export "sum" (func $sum))
  • ✓ Import JS functions into WASM
  • ✓ Export WASM functions for JS
  • ✓ Namespace organization

Why Use WAT?

WAT is useful for:

  • ✓ Reading and editing modules
  • ✓ Debugging before converting to binary
  • ✓ Understanding low-level code structure
  • ✓ Learning WebAssembly fundamentals

Convert between WAT and binary with wasm2wat and wat2wasm tools.

Mini WASM Experiment 1(Unoptimized)

Experiment Overview

  • Goal: Compare WASM speed across Safari, Chrome, Firefox
  • Implementation: C++ function with heavy computation
  • Compiled using Emscripten in unoptimized manner
  • Generated: .html, .wasm and .js files
  • Modified HTML for testing

C++ Code

extern "C" {

int heavy(int n) {
    int sum = 0;
    for(int i = 0; i < n; i++) {
        sum += (i % 10);
    }
    return sum;
}

}

extern "C" tells the C++ compiler not to mangle the function name, so it can be called from JavaScript or C with a simple, predictable name.

Compilation Command

emcc code.cpp -o code.html \
-s EXPORTED_FUNCTIONS='["_heavy"]' \
-s EXPORTED_RUNTIME_METHODS='["cwrap"]'
  • -o code.html: Generate HTML + JS + WASM files
  • -s EXPORTED_FUNCTIONS: Expose C++ function heavy to JavaScript
  • -s EXPORTED_RUNTIME_METHODS: Expose runtime helpers like cwrap for easy JS calls

Custom HTML Modifications

Code Block 1:

This code adds a textarea to show output, buttons to run JS or WASM functions, and a paragraph to display the result.

Code Block 2: 


let heavyWASM;
Module.onRuntimeInitialized = function() {

	heavyWASM = Module.cwrap('heavy', 'number', ['number']);

	console.log("WASM Ready ✅");
};
function heavyJS(n) {
	let sum = 0;
	for(let i = 0; i < n; i++) {
  		sum += (i % 10);
	}
	return sum;
}

function runJS() {
	const N = 5e7;
    console.time("JS Time");
    let res = heavyJS(N);
    console.timeEnd("JS Time");
    document.getElementById("result").innerText = "JS Result: " + res;
}

function runWASM() {
	const N = 5e7;
    console.time("WASM Time");
    let res = heavyWASM(N);
    console.timeEnd("WASM Time");
    document.getElementById("result").innerText = "WASM Result: " + res;
}

This code defines a JS version and a WASM version of heavy, then runs and times each when the buttons are clicked, displaying the results.

Running Local Server

Browsers block loading .wasm files over file://. To run the demo properly, start a local HTTP server: 

python3 -m http.server 8000

Then open: http://localhost:8000/code.html in your browser.

  • Ensures the browser can load .wasm via HTTP.
  • Enables proper execution of JS and WASM functions.

Browser WASM Performance Results

WASM Execution time comparison across browsers:

  • 🏅 Safari ~75ms (fastest WASM)
  • 🥈 Firefox: ~147ms (slightly slower WASM)
  • 🥉 Chrome: ~156ms (slowest WASM)

Browser JS Performance Results

JS Execution time comparison across browsers:

  • 🏅 Firefox: ~59ms (fastest JS)
  • 🥈 Chrome: ~82ms (slightly slower JS)
  • 🥉 Safari: ~228ms (slowest JS)

Safari Results

WASM Execution Time: ~75ms

Firefox Results

WASM Execution Time: ~147ms

Chrome Results

WASM Execution Time: ~156ms

Key Observations

  • WASM is ~3× faster than JS on Safari.
  • JS is faster than WASM on Firefox and Chrome for this test.
  • Browser performance for JS vs WASM is highly dependent on the JS engine.
  • WASM benefits simple computations in slower JS engines.
  • For larger/complex computations, WASM usually outperforms JS.

Conclusions

  • WASM was fastest on Safari (75 ms) because Safari’s JS engine, JavaScriptCore, is slower on loop-heavy numeric computations, so WASM gives a clear speedup.
  • On Firefox (JS 59 ms vs WASM 147 ms) and Chrome (JS 82 ms vs WASM 156 ms), JS was faster because SpiderMonkey (Firefox) and V8 (Chrome) have highly optimized JIT engines for simple numeric loops, sometimes outperforming WASM.
  • The experiment highlights that JS vs WASM performance is browser-dependent, not universally in favor of WASM.
  • Simple computations with small loops can show JS outperforming WASM due to WASM call overhead.
  • WASM shows clear advantages for large or complex computations, where its near-native speed dominates JS overhead.

Compilation Command

-s WASM=1 \
-s EXPORTED_FUNCTIONS='["_heavy"]' \

  • -O3: Apply maximum optimisation level
  • -s WASM=1: Enable WASM output
  • -s EXPORTED_FUNCTIONS: Expose C++ function heavy to JavaScript
  • -s EXPORTED_RUNTIME_METHODS: Expose runtime helpers like cwrap for easy JS calls
  • -o code1.js: Generate JS + WASM files

Why Use WebAssembly?

⚡ Performance

Near-native execution speed for compute-heavy tasks like gaming, simulations, and real-time processing.

🔒 Security

Runs in a sandboxed environment with memory-safe execution model and controlled access.

🌍 Portability

Works across Chrome, Firefox, Safari. Same binary runs everywhere without recompilation.

🧠 Language Flexibility

Write in C, C++, or Rust. Compile once and run on the web.

Challenges of WebAssembly

🔗

No Direct DOM Access

Requires JavaScript as a bridge between WASM and browser APIs.

⏳

Startup Overhead

Load time + compilation can add latency, especially for large modules.

🔄

JS ↔ WASM Call Cost

Frequent function calls reduce performance gains due to crossing boundaries.

⚠️

Evolving Ecosystem

Advanced features not fully standardized; tooling still maturing.
